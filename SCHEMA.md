# JSON Schema Documentation

This document describes the two data files generated by the Python scripts and consumed by the React website.

---

## File 1: leagueData.json

Generated by `scripts/fetch_league_data.py`. Contains all match data, registrations, and leaderboards.

### Root Object

```typescript
{
  lastUpdated: string,           // ISO 8601 timestamp (UTC)
  leagues: {
    [leagueName: string]: League
  },
  globalLeaderboard: Player[]
}
```

### Types

#### League

```typescript
{
  subLeagues: {
    [subLeagueName: string]: SubLeague
  }
}
```

#### SubLeague

```typescript
{
  rounds: Round[],
  leaderboard: Player[],
  record?: { wins: number, losses: number, draws: number },
  diagnostics?: {
    mergedFrom: string[],
    ambiguousMatches: {
      matchId?: string,
      name: string,
      reason: string
    }[],
    dateResolvedMatches?: {
      matchId?: string,
      name: string,
      reason: string
    }[],
    observedRounds: string[],
    missingRounds: string[]
  }
}
```

`diagnostics.missingRounds` reports numbered gaps between observed `R<n>`
rounds. It does not create placeholder matches, and it remains empty when a
sub-league has fewer than two numbered rounds.

#### Round

```typescript
{
  round?: string | null,             // e.g. "R1", "M1" (same-day match), "NA", or null
  status: "open" | "in_progress" | "finished",
  matchId: string,                   // API identifier
  matchUrl: string,                  // API URL
  matchWebUrl?: string,              // Web-friendly URL
  name: string,                      // Original match title
  startTime?: number | null,         // Unix seconds
  endTime?: number | null,           // Unix seconds
  boards: number,                    // Number of boards
  matchResult: {
    ourScore: number,
    opponentScore: number,
    result: "win" | "lose" | "draw" | "forfeit" | "double forfeit" | "win by forfeit" | "unknown"
  },
  playerStats: {
    [username: string]: {
      games: number,
      wins: number,
      draws: number,
      losses: number
    }
  },

  // For open matches with registration data
  registrationData?: {
    type: "roster",
    ourRoster: { username: string, rating?: number, timeoutPercent?: number | null }[],
    oppRoster: { username: string, rating?: number, timeoutPercent?: number | null }[]
  } | null,

  // For open matches with board assignments
  boardsData?: {
    boardNumber: number,
    ourPlayer?: string,
    ourRating?: number | null,
    ourTimeoutPercent?: number | null,
    oppPlayer?: string,
    oppRating?: number | null,
    oppTimeoutPercent?: number | null,
    ratingDiff?: number | null
  }[],

  registeredPlayers?: { our: number, opponent: number },
  minTeamPlayers?: number            // Minimum players required
}
```

#### Player (in leaderboard)

```typescript
{
  username: string,
  games: number,
  wins: number,
  draws: number,
  losses: number,
  points?: number                    // Calculated: wins + 0.5 * draws
}
```

### Key Features

- **Status**: Open (registration), In Progress (playing), or Finished
- **Forfeit Detection**: Automatic for completed matches (0-0 score)
- **Registration Data**: Rosters and board assignments for upcoming matches
- **Leaderboards**: Sorted by points (desc), then games (asc)

## File 2: playerRatings.json

Generated by `scripts/fetch_player_ratings.py` from the cached
`chessteamdata.com/api/members` response. This is a compact current-rating
lookup, not rating history. It contains only players who both appear in this
site's league history and are present in the latest valid member-service
response.

The member service is deployment-specific and only serves clubs provisioned by
the site owner. Forks tracking another club must supply a compatible ratings
source or disable ratings-dependent features; league and historical data do not
depend on this service.

```typescript
{
  schemaVersion: 1,
  generatedAt: string,
  source: "member-service",
  sourceStatus: "ok" | "stale" | "unavailable" | "disabled",
  sourceUpdatedAt: string | null,
  lastAttemptedAt: string | null,
  membershipStatus: "verified" | "unverified",
  membershipVerifiedAt: string | null,
  recruitmentEnabled: boolean,
  players: {
    [username: string]: {
      username: string,
      dailyRating: number | null,
      rating960: number | null,
      memberServiceTimeoutPercent: number | null,
      fetchedAt: string,
      lastSeenAt: string
    }
  }
}
```

Recruitment must use an entry only when `recruitmentEnabled` is true,
`membershipStatus` is `"verified"`, and the requested variant rating is numeric.
The member service's `updateDate` is
stored as `sourceUpdatedAt`; its expected daily or weekly cadence is accepted,
so an otherwise valid cached snapshot remains usable when the service is
temporarily unavailable. A member who leaves the club is removed during the
next successful member-service validation; their historical league records
remain unchanged. A failed validation never removes entries.

The importer maps each member-service `members[]` record's `username`, `daily_rating`,
`daily_960_rating`, and `timeout_percent` to the corresponding player fields.
The response-level `updateDate` is an epoch-millisecond source timestamp. A
response is valid only when it contains both a member list and a valid positive
`updateDate`. When the service is disabled, the ratings cache is unavailable
and recruitment is disabled; match-based league and timeout-risk processing
continues normally.

## File 3: timeoutData.json

Generated by `scripts/enrich_timeouts.py`. Contains timeout risk analysis for players registered in open matches.

### Root Object

```typescript
{
  generatedAt: string,               // ISO 8601 timestamp (UTC)
  riskThresholdPercent: number,      // Timeout % gate: players above this are flagged
  riskConfig: {
    highTimeoutPct: number,          // Timeout % factor threshold for HIGH
    highDailyTimeoutCount: number,   // Daily timeout count factor threshold for HIGH
    highSubLeagueTimeoutCount: number, // Sub-league timeout count factor threshold for HIGH
    highMinFactors: number,          // Min factors that must be met to be rated HIGH
    lowMaxTimeoutPct: number,        // Condition A: pct upper bound for LOW
    lowMaxDailyTimeoutCount: number, // Condition A: daily timeout ceiling for LOW
    lowMaxTimeoutPctRecent: number,  // Condition B: pct upper bound for LOW (recency gate)
    lowRecencyDays: number           // Condition B: min days since last timeout for LOW
  },
  players: {
    [username: string]: PlayerRisk
  }
}
```

### Types

#### PlayerRisk

```typescript
{
  timeoutPercent: number | null,     // Selected match/fallback timeout % used for risk
  standardTimeoutPercent: number | null, // Standard value from match registration
  chess960TimeoutPercent: number | null, // Chess960 value from match registration
  timeoutPercentSource: string,      // Match or member-service-fallback provenance
  memberServiceTimeoutPercent: number | null, // Optional standard fallback
  dailyRating: number | null,        // Current 1-day chess rating from member service
  rating960: number | null,           // Current Chess960 rating from member service
  totalLeagueTimeouts90Days: number, // Timeouts in league matches (last 90 days)
  subLeagueTimeouts: {
    [league: string]: {
      [subLeague: string]: number    // Timeouts per sub-league (all-time)
    }
  },
  dailyTimeouts: {
    1day: { count: number, lastTimeoutDate: string | null },
    2day: { count: number, lastTimeoutDate: string | null },
    3day: { count: number, lastTimeoutDate: string | null }
  },
  riskFlag: boolean,                 // True if timeoutPercent > threshold
  riskLevel: "HIGH" | "MEDIUM" | "LOW" | null,  // Risk tier (null if not flagged)
  riskReason: string | null          // Human-readable explanation
}
```

### Risk Levels

A player is only assigned a risk level when `riskFlag` is `true` (i.e. their
`timeoutPercent` exceeds `riskThresholdPercent`). The tier thresholds are all
configurable via `script_params.json` and are reflected in `riskConfig`.

- **HIGH**: At least `highMinFactors` (default 2) of the following are true:
  - `timeoutPercent > highTimeoutPct` (default 50%)
  - Recent daily timeouts ≥ `highDailyTimeoutCount` (default 10)
  - Sub-league timeouts ≥ `highSubLeagueTimeoutCount` (default 2)
- **LOW**: Either condition is satisfied:
  - Condition A: `timeoutPercent < lowMaxTimeoutPct` (default 30%), no sub-league timeouts, and daily timeouts < `lowMaxDailyTimeoutCount` (default 10)
  - Condition B: `timeoutPercent < lowMaxTimeoutPctRecent` (default 40%), no sub-league timeouts, and last timeout is older than `lowRecencyDays` days (default 60)
- **MEDIUM**: `riskFlag` is true but neither HIGH nor LOW criteria are met
- **null**: Not flagged (`timeoutPercent ≤ riskThresholdPercent`)

### Data Collection

- **Player registration**: Scans `status == "open"` rounds in `leagueData.json`
- **Player roster**: Reads `registrationData.ourRoster` (registered for upcoming match)
- **Match API registration data**: Supplies variant-specific timeout percentages
- **Member service cache**: Supplies current daily/Chess960 ratings and an optional standard timeout fallback
- **Chess.com API**: Fetches game archives only for deeper timeout history of at-risk players
- **Coverage**: Only includes unique players across open matches

# JSON Schema for League Data

This document describes the actual structure of `leagueData.json` produced by `scripts/fetch_league_data.py` and consumed by the React UI. It includes fields for match metadata, results (including forfeit detection), registration information, and board-level rating data.

## Root Object

```typescript
{
  lastUpdated: string,           // ISO 8601 timestamp (UTC)
  leagues: {
    [leagueName: string]: League
  },
  globalLeaderboard: Player[]
}
```

## Types

### League

```typescript
{
  subLeagues: {
    [subLeagueName: string]: SubLeague
  }
}
```

### SubLeague

```typescript
{
  rounds: Round[],
  leaderboard: Player[],
  record?: { wins: number, losses: number, draws: number },
  diagnostics?: {
    mergedFrom: string[],
    ambiguousMatches: {
      matchId?: string,
      name: string,
      reason: string
    }[],
    dateResolvedMatches?: {
      matchId?: string,
      name: string,
      reason: string
    }[],
    observedRounds: string[],
    missingRounds: string[]
  }
}
```

### Round

```typescript
{
  round?: string | null,             // e.g. "R1", "M1" (same-day match), or "NA"; may be null initially
  status: "open" | "in_progress" | "finished",
  matchId: string,                   // API identifier (often full API URL)
  matchUrl: string,                  // API URL
  matchWebUrl?: string,              // Web-friendly URL (https://www.chess.com/club/matches/{id})
  name: string,                      // Original match title
  startTime?: number | null,         // Unix seconds (may be null)
  endTime?: number | null,           // Unix seconds (may be null)
  boards: number,                    // Number of boards in the match
  matchResult: {
    ourScore: number,
    opponentScore: number,
    result: "win" | "lose" | "draw" | "forfeit" | "double forfeit" | "win by forfeit" | "unknown"
  },
  playerStats: {
    [username: string]: {
      games: number,
      wins: number,
      draws: number,
      losses: number
    }
  },

  // Registration-related fields (present for registration/open matches)
  registrationData?: {
    // If boards are not yet assigned this will be a roster object
    type: "roster",
    ourRoster: { username: string, rating?: number }[],
    oppRoster: { username: string, rating?: number }[]
  } | null,

  // If boards are assigned, boardsData is an array of per-board objects
  boardsData?: {
    boardNumber: number,
    ourPlayer?: string,
    ourRating?: number | null,
    oppPlayer?: string,
    oppRating?: number | null,
    ratingDiff?: number | null
  }[],

  registeredPlayers?: { our: number, opponent: number },
  minTeamPlayers?: number  // Present for all matches, extracted from match settings
}
```

### Player

```typescript
{
  username: string,
  games: number,
  wins: number,
  draws: number,
  losses: number,
  points?: number
}
```

## Additional Notes

- `matchId` and `matchUrl` are often full API URLs (e.g. `https://api.chess.com/pub/match/1895389`). `matchWebUrl` is provided for convenient linking to the chess.com UI.
- `round` may be parsed from the match title (e.g. `R1`). For a roundless
  sub-league whose matches all start on the same UTC calendar day, the script
  assigns deterministic simultaneous-match labels `M1`, `M2`, etc. Other
  unresolved non-numbered matches use `NA`, `NA-2`, etc.; these are not
  synthesized rounds.
- `registrationData` is present for `open` matches; if boards are not assigned it provides sorted rosters for strategic planning. If boards are assigned `boardsData` will be an array with ratings per board.
- `registeredPlayers` provides simple counts used by the UI to show registration progress.
- `minTeamPlayers` is extracted from match settings and available for all matches (not just registration). Used for forfeit detection.
- `playerStats` contains only stats aggregated from matches where our club's players participated (the script filters to our club when building per-player stats).

### Forfeit Detection

For **finished** matches with a 0-0 score, the script automatically detects forfeits based on player counts vs. `minTeamPlayers`:
- **"forfeit"**: We failed to meet minimum players (we lose)
- **"double forfeit"**: Both teams failed to meet minimum (we lose)
- **"win by forfeit"**: Opponent failed to meet minimum (we win)

This only applies to completed matches and does not affect registration warnings for open matches.

### Timeout Tracking

Timeout data combines match-level results with an optional member-service fallback:

1. **For in_progress/finished matches**: Counts games where a player timed out by checking the game result (`"timeout"` value in `played_as_white` or `played_as_black`). These are tracked in the `timeouts` field and also count toward `losses`. Only included in the output if the count is greater than 0.

2. **For risk enrichment**: Reads variant-specific `timeout_percent` values from
   open-match registration data already fetched into `leagueData.json`. For a
   Chess960 match, the highest available standard/Chess960 value is used. If a
   standard value is missing and configured, the member-service standard value
   is used as a fallback.

The match API remains the source for match-specific timeout counts, while the
member service supplies optional current ratings and fallback data. No player
`/stats` request is required by this workflow.

## Sorting & Calculations

- Leaderboards are computed by summing `wins` + 0.5 * `draws` into `points` and sorted by points (desc) then games (asc).
- Sub-league `record` is derived from `matchResult.result` values across rounds.

## Migration / Compatibility

If you adapt the script for another club or change `LEAGUE_PREFIXES`, ensure your match titles place the league prefix first and follow a consistent pattern so the `parse_match_title` logic can extract `league`, `subLeague`, and `round` as intended.
